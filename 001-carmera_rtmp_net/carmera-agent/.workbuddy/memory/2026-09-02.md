### 三个设计冲突及处理方案（待用户确认）
1. **1080P30 vs 240×240@8fps**：不写死分辨率，bbox 按实际协商分辨率归一化还原；`video_width/height` 填协商值。
2. **「每 6 帧取 1 帧」在 8fps 源上失效**（=1.33fps）→ 改为**基于 PTS 的时间间隔采样**（`ai.fps=5` → 200ms 一帧），30fps/8fps 源都成立。
3. **帧共享用 tee**：`videoconvert → [caps] → tee ├→ 编码器→RTSP（原链路） └→ queue(leaky)→videoconvert→appsink（新增）`。
   - AI 关闭时不插 tee/appsink → 管线字符串与现状逐字相同（零风险）
   - AI 分支 `queue max-size-buffers=2 leaky=upstream` + `appsink max-buffers=1 drop=true` → 满则丢旧留新，绝不反向阻塞视频
   - appsink 取**原始分辨率 RGB**，letterbox 在 C++ 做（不用 GStreamer 拉伸到 640，否则宽高比失真致 bbox 变形）

- **`PATHEXT=.CPL` 沙箱环境**导致 PowerShell `& exe` 把 .exe 当"文档"，整个 build 静默 no-op，输出空 log。修复：`scripts/build-msvc.ps1` 头部补 `if ($env:PATHEXT -notmatch '\.EXE') { $env:PATHEXT = '.COM;.EXE;.BAT;.CMD;.VBS;.VBE;.JS;.JSE;.WSF;.WSH;.MSC;.CPL' }`

- **RTSP 连接失败的根因不是管线**：测试时最初是 mediamtx 已经死了（被回收）所以 RTSP 拒绝；之后 mediamtx 常驻后 STREAMING 稳定

### 关键设计
- AI 线程只做「编码 + 短锁入队 + notify_one」，**绝不联网**；阻塞工作全在发送线程
- 队列有界（默认 8），满则丢最老；**离线退避窗内直接丢弃**（不过时 metadata 无价值），所以断服时队列不膨胀
- `StreamController` 里 `meta_` 声明在 `ai_` **之前**，保证析构时消费者比生产者活得久
- `set_transport()` 允许单测注入替身

### 最重要的坑：WinHTTP 惰性连接
- **现象**：95s 断服长跑里恢复确实发生了（`sent` 110→286 恢复增长、`failed/dropped` 冻结），
  但 `reconnect=0`、无 `connection restored` 日志。
- **根因**：`WinHttpConnect` 对不存在的端口也返回成功，`transport->connected()` 一直是 true，
  断连只在 `send()` 往返失败时暴露。旧实现用 `connect_failures_` 驱动重连计数，因此永不触发。
- **修法**：重连状态机改由**往返结果**驱动 —— `send()` 失败 → `register_failure(attempted)` 置
  `offline_`（`std::atomic<bool>`）、算退避窗 `next_connect_`；首次成功后 `offline_` 由真变假才
  `++reconnect_` 并打 `connection restored`；`ever_connected_` 区分"首次连上"与"断后恢复"。
  `stats().connected` 取 `transport->connected() && !offline_`。
- **锁定回归**：新增单测 `metadata_reconnect_counted_on_recovery`，用 `FlakyTransport`
  （`connect()` 永不失败、只在前 3 次 `send()` 失败）断言 `reconnect==1 && failed==3`。
