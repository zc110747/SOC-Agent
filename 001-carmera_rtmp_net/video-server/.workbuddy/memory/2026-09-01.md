## 联合运行打通：carmera-agent（C++）↔ video-server（Go）

### 核心约束：全局只能有一个 MediaMTX
- video-server 启动时会**自己拉起** MediaMTX 子进程，且**只有这个实例**开了控制 API（`:9997`）；
  monitor 每 3s 轮询 `/v3/paths/list` 发现摄像头，靠的就是它。
- `carmera-agent/` 里也有 `mediamtx.yml` + `start-camera-agent.bat`，**联合运行时绝不能执行** ——
  会起第二个 MediaMTX 抢 `:8554`，且它没有 API，服务器根本看不到那路流。
- 正确做法：直接启动 `camera-agent.exe`，让它推到服务器那个 MediaMTX 上。

### UVC 摄像头必须 --auto
- 本机摄像头 `UVC Control` 原生只有 **240×240@8fps**（`camera-agent --list` 实测）。
- 父级 `start-demo.bat` 原先用默认 1280×720@30 调 agent → caps 协商失败 → 进不了 PLAYING
  → 重连死循环。已修复：给 agent 加 `--auto`（原生协商）。两个启动脚本均已默认带上。

### 代码改动（video-server）
- `internal/mediamtx/manager.go`：Path 增加 `Tracks2`（含 `codecProps.width/height`）。
- `internal/stream/stream.go`：Stream 增加 `Width/Height` + `Resolution()`；
  新增 `videoResolution()` / `codecPropInt()` 宽容解析（float64/int/string）。
- `internal/monitor/monitor.go` + `internal/camera/repo.go`：
  `UpsertByStreamPath` 增加 `resolution` 参数，把 MediaMTX track 里的真实分辨率回写 cameras 表；
  **空值不覆盖**已有数据（避免解析前的扫描把用户设的值清空）。
- 修掉了自动注册时 `resolution=""` / `fps=0` / `bitrate=0` 的缺口，Web UI 现在能显示 240×240。

### 新增文件
- `config/config.joint.yaml` —— 联合运行专用配置，**HTTP 从 8080 改到 8081**。
  因为本机 `:8080` 会被 `ApplicationWebServer` 抢占（实测 PID 8684），演示会随机起不来。
- `scripts/start-joint.bat` —— 一键拉起（清理 → server → 等 health → agent --auto → 等注册 → 开浏览器）。
  从 config 反解端口，不硬编码；摄像头索引用 `--list` 自动挑选。
- `scripts/stop-joint.bat` —— 停全部（`/T` 杀进程树，含 MediaMTX 子进程）。
- `scripts/verify_joint.py` —— 真实推流端验收（区别于 verify_e2e.py 的 ffmpeg 合成流）。
  7 阶段：枚举摄像头 → server 三态 → agent STREAMING → 自动注册 → ffprobe 解码 →
  分辨率一致性 → WHEP 可达性。**实测 PASS=11 FAIL=0 INFO=2**。

### 踩坑
- `ffprobe` 对直播流**不能加 `-count_frames`** —— 永不返回，会把整条命令挂死（我第一次就被 SIGTERM）。
  用 `timeout` + 不带 count_frames。
- PowerShell 工具跑 `.bat`：`& $bat *>&1 | Out-File` 可用；但**不能** `cmd.exe /c`（被安全策略拦截），
  且**不能**把 `& $bat` 与 `+=` / 管道混用（会整体失败、文件不落盘）。
- 沙箱 PowerShell 会话结束会回收 `start` 拉起的独立窗口，进程随后消失 —— **不是脚本缺陷**，
  双击运行正常。要留存活进程用 Bash 的 `run_in_background`。
- PowerShell 5.1 不支持三元 `?:`（写环境检查脚本时踩到）。

## 不同分辨率/帧率摄像头自适应（换 720p@30/60、1080p@30 也能用）

### 两个已知问题已修（用户报：帧率不显示 + 开流约 5s 才出画面）
1. **帧率不显示**：MediaMTX 控制 API 的 `tracks2[].codecProps` 只给 width/height/profile/level，
   **不含 fps，也不含 SPS**（已 curl `/v3/paths/get/camera01` 验证）。唯一可靠来源是 `ffprobe` 的
   `avg_frame_rate`（实测 240×240 给出 `8/1`，与真实 8fps 一致）。
2. **首帧 ~5s 延迟根因**：`x264enc key-int-max` 按**帧**计，默认 30 帧；8fps 下 30 帧 = 3.75s 才一个
   IDR，WebRTC 播放端必须等下一个 IDR 才能出首帧 → 体感 ~5s。

### 修复方案
- **Agent 侧（carmera-agent/src/pipeline/video_pipeline_gst.cpp）**：`--auto` 原生协商下，PLAYING 后
  有界轮询等 caps（最多 30×100ms，避 live source 协商未完成），拿到真实 `neg_fps_/neg_w_/neg_h_`；
  若 `auto_res_ && neg_fps_>0` 且 `desired=clamp_int(neg_fps_,1,300) != built_keyint_`，一次性重建管线：
  `keyint_corrected_=true`，`rebuild_with_keyint(desired)` 设 `keyframe_interval=desired`（≈1 秒 GOP），
  auto_res 下同时按 `auto_bitrate(w,h,fps)`（0.07 bit/像素，800~12000kbps 钳制）重设码率。
  `stop()` / bus 的 ERROR/EOS 在 `rebuilding_` 时**不**误触 DISCONNECTED 重连。
- **Server 侧**：
  - `internal/camera/repo.go`：`UpsertByStreamPath` 扩展 `(resolution, fps, bitrate)`，动态拼 SET，
    **`fps>0` / `bitrate>0` / `resolution!=""` 才写，0/空不覆盖**已有数据。
  - `internal/stream/stream.go`：List 填 `BytesReceived`。
  - `internal/monitor/monitor.go`：`scan()` 用 `bytesReceived` 跨扫描增量算码率（需 2 样本，dt>0.5s）；
    `maybeProbeFps()` 每路径最多每 120s 一次异步 `go probeFps()` → `ffprobeFps()` 取 `avg_frame_rate`，
    范围 1~1000；`exec.LookPath("ffprobe")` 缺失则跳过不报错。

### 端到端验收（本机 240×240@8fps 原生 UVC）
`python3 scripts/verify_joint.py`（PATH 带 GStreamer + ffmpeg bin）→ **PASS=14 FAIL=0 INFO=2**：
- `frame rate propagated to API (ffprobe)` = 8fps；`API fps matches agent-negotiated fps` = api8/agent8
- `bitrate propagated to API (bytesReceived delta)` = 729kbps
- agent 日志确认 GOP 自适应：`Negotiated 8fps (240x240); rebuilding with keyint=8 for <=1s GOP (was 30)`，
  无 reconnect/ERROR 循环，稳定 STREAMING。

### 换高分辨率摄像头为何能工作（无硬件实测，逻辑保证）
`--auto` 不强制 caps → 摄像头原生协商；agent 按真实 fps 重建 GOP（720p@30→keyint30、720p@60→keyint60、
1080p@30→keyint30，均 ≈1s）；码率 auto_bitrate 估算（1080p@30≈6000 / 720p@30≈2000 / 720p@60≈4000 kbps）；
server 侧 ffprobe 取任意 fps、bytesReceived 增量取任意码率 → Web UI 自动显示。README 7.4 已写用法与排错。

## WebRTC 首帧 ~4-5s 延迟根因与修复（NVENC `gop-size`）

### 现象
`--auto` 下 keyint 已重建为 8（≈1s GOP），但浏览器 WebRTC **首帧仍 4-5s**，connected 后实时。
用户原话："webrtc首次显示还是有延时，大概4-5s(后续成功显示后没有延时)"。

### 根因（隐蔽）
`encoder_element()` 只给 **x264 分支**加 `key-int-max`；本机实际用 **`nvh264enc`**（有 NVIDIA GPU，
`pick_encoder()` 优先 NVENC）。**nvh264enc 的 GOP 属性是 `gop-size`（gst-inspect 确认：
`gop-size : Number of frames between intra frames (-1 = infinite)`），不是 `key-int-max`**。
NVENC 分支漏设 → GOP 校正被**静默丢弃**（gst_parse_launch 对未知属性只告警）→ NVENC 用默认 GOP
（~7-8s）→ WebRTC 播放端必须等下一个 IDR，体感 4-5s。

### 实测对照（ffprobe 数 15s 内关键帧）
- 修复前：仅 2 个关键帧（≈7.5s GOP）→ 对应 4-5s 首帧。
- 修复后（NVENC `gop-size=8`）：13 个关键帧（≈1s GOP）→ 首帧 ≤1s。

### 修复
`encoder_element()`：
- NVENC 分支：`gop-size=N`（替换缺失的 key-int-max）。
- x264/mfx 分支：保持 `key-int-max=N`。
- x264 分支补 `repeat-sequence-header=true`（每个 IDR 自带 SPS/PPS，断线重连不必等下一关键帧）。
零警告重建通过（`cmake --build build-msvc --target camera-agent`，env 注入绕过 reg.exe 黑名单）。

### 教训（跨项目通用）
不同编码器 GOP 属性名不同：**x264enc / mfxh264enc = `key-int-max`；nvh264enc = `gop-size`**。
统一用 `key-int-max` 对 NVENC 是静默 no-op，会让"低延迟 GOP 校正"完全失效——改 GOP 前务必先
`gst-inspect-1.0 <enc>` 确认属性名。MediaMTX 作者 aler9 定论：WebRTC 首帧延迟 = 等下一个 I 帧的
时间，缩短 I 帧间隔是唯一解法。
